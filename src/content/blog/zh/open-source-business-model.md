说实话，Autional 的开源策略从一开始就充满争议。

内部有过激烈争论——有人主张「要做开源就全开，否则就是伪开源」，也有人反问「全开源团队怎么活下去，靠卖 T 恤吗？」我们最终选择了一条中间路线：**Open Core 模式**。本文诚实地谈这个决定背后的理由、两年的实践，以及踩过的坑。

> **合规声明**：本文提及的合规框架（SOC 2、GDPR 等）代表 Autional 的设计对齐目标，不构成认证已取得的法律陈述。开源代码的安全审计责任由使用者承担。

## 什么是 Open Core 模式

Open Core 模式的核心逻辑很简单：

- **核心功能开源**：门户、设计系统与 SDK 等核心组件以 AGPL-3.0 许可证在 GitHub 组织页开源发布，平台当前自托管开源可用。任何人都可以免费使用、修改与部署。
- **高级功能商业化**：面向企业的能力——合规管理（SOC 2/GDPR 自动化）、计费系统、高级安全（UEBA 行为分析）、企业 SSO 连接器、SLA 保障、专属技术支持——通过私有化部署授权或订阅制云服务（云托管在路线图中，即将推出）的方式提供。

这个模式的本质是：**我们把解决共性需求的基础层开源，把解决企业场景的增值层商业化。** 这不是钓鱼式营销——开源部分不是演示广告，而是可以真实使用的组件。我们不会故意在开源版本里留缺口，然后说「这个功能只有付费版才有」。

## 为什么不全开源

这是我们被问得最多的问题。答案分两部分：理想与现实。

### 理想主义的答案

我们相信开源的价值——透明建立信任，社区驱动创新，用户不必担心被厂商锁定。如果我们全开源还能不破产，我们会毫不犹豫地这么做。

但身份认证是一个特殊的领域。它不像前端框架或编程语言——身份系统承载着用户最敏感的凭证数据。开源意味着任何人都能读到你的密码哈希逻辑、你的会话令牌生成算法、你的 OAuth 授权流程。这对安全审计是好事，但如果商业模式不可持续，开源项目最终会变成无人维护的鬼城——那才是对用户最大的不负责。

我们不希望 Autional 成为又一个「维护者倦怠、项目归档」的开源故事。**可持续的商业模式，才是对开源社区最大的尊重。**

### 现实主义的答案

Autional 目前是一支 15 人的团队，每月的基础设施成本（数据库、缓存、消息队列、监控、CDN）都需要持续投入。如果完全开源且没有商业服务，我们付不起这些账单。

全开源还意味着要跟云厂商竞争。AWS 可以把我们的代码打包成托管服务零成本售卖，而服务器账单与维护成本由我们承担。这不是危言耸听——Elasticsearch 与 MongoDB 都经历过这场挣扎，最终不得不修改开源许可证来应对。

Open Core 模式让我们能同时做两件事：**用开源版赢得开发者信任与社区反馈，用商业版产生可持续收入并反哺开源开发。**

## 哪些是开源的

我们的开源范围经过审慎界定：

**核心开源（GitHub 组织页，AGPL-3.0）：**

| 项目 | 说明 |
|--------|-------------|
| 门户界面 | 品牌门户、展示站与管理界面的前端实现 |
| 设计系统与组件库 | @autional/ui、@autional/tokens 等组件库与设计令牌 |
| SDK 与 npm 软件包 | @autional/react、@autional/onboard、@autional/shared 等已发布软件包 |

**商业授权（私有化部署；云托管在路线图中）：**

| 模块 | 说明 |
|--------|-------------|
| compliance-service | SOC 2 / GDPR / 等保合规自动化 |
| billing-service | 计费、套餐、发票 |
| audit-service 高级功能 | 哈希链完整性校验、SIEM 集成、合规报告 |
| 企业 SSO 连接器 | SAML、LDAP、Azure AD、Okta 集成 |
| UEBA 行为分析 | 用户实体行为分析、风险评分引擎 |
| 专属支持 | SLA 保障、架构咨询、安全事件响应 |

关键原则：**核心认证能力的完整性不受商业授权影响。** 即使只用开源版，你也能够运行一套完整的身份系统——注册、登录、MFA、OAuth、会话管理，每一项必需功能都在。

## 这个模式的收益

### 透明建立信任

身份系统的安全性必须经得起审计。开源意味着任何安全研究者都可以审阅我们的代码，无需签署 NDA，也无需成为付费客户。这不是营销话术——公开的代码仓库让外部审阅成为常态，也让问题更早暴露、更早修复。

采用者同样受益——在安全尽职调查时，可以直接审阅代码，而不是只依赖安全架构文档与口头承诺。

### 社区驱动的创新

开源社区的反馈速度远超任何内部测试团队。组件与 SDK 的 API 设计、文档的详略取舍、设计系统与主题能力，都欢迎来自真实使用场景的反馈，并会直接影响这些方向。

社区贡献者不需要是专职员工——他们只需在自己的使用场景里发现问题、提出方案。这种分布式创新在闭源模式下无法复制。

### 可持续的商业循环

开源版是产品最强的销售渠道。开发者先在自己的项目里用开源组件；当团队壮大、需要合规支持或企业功能时，再评估商业方案。这条路让商业转化建立在使用体验之上，而不是建立在陌生的销售拜访上。

循环大致是这样：

```
Open source version → Developer experience → Team adoption → Enterprise need arises → Commercial subscription
    ↑                                                                                      │
    └──────────────── Income reinvests in open source development ←────────────────────────┘
```

## 这个模式的挑战

说实话，Open Core 模式并不完美。以下是我们在实践中遇到的真实问题：

### 边界管理：什么该开源，什么不该

这是最难的决策。每次开发新功能，团队都要争论：这属于基础能力还是增值能力？

我们的决策框架：
1. 这个功能是否影响核心认证能力的完整性？→ 是 → 开源
2. 这个功能是否只有规模化企业才需要？→ 是 → 商业化
3. 这个功能是否会成为行业标准？→ 是 → 开源（我们不希望 Autional 的独特实现成为用户迁移的壁垒）

但框架并非万能。MFA 的高级策略引擎（自适应风险评分）算基础还是增值？团队争论了两周才达成共识：核心 MFA 能力（TOTP、WebAuthn）随开源版本提供，自适应风险引擎作为商业能力。有人会说这是人为的切割——我们理解这种质疑，但这也是现实：风险引擎的开发与维护需要持续的威胁情报投入，靠开源社区的志愿模式无法支撑。

### 社区信任：避免「伪开源」

Open Core 模式最大的风险是被认为「伪开源」——一个为了刷 GitHub Stars 的营销噱头，实际产品却不能用。

我们通过几种方式化解这个风险：
- **开源部分是功能完整、可独立使用的。** 不是 Demo，不是阉割版。
- **公开路线图。** 产品规划（包括开源与商业方向）都在[路线图页面](https://www.autional.cn/roadmap)上公开。
- **开源版没有部署规模限制。** 不会出现「开源版最多支持 1000 用户」这类限制。
- **社区贡献的 PR 不会被拒。** 只要代码质量达标，社区贡献的功能就会合并进开源版——即使它与某个商业功能有重叠。

### 企业诉求：私有化部署要求源码可见

私有化部署场景下，查看源码往往是一项硬性要求。我们的方案是：**商业授权包含源码访问权**——客户可以审阅、修改，但不能二次分发。这平衡了客户的安全审计需求与我们的商业可持续性。

## 来自其他公司的验证

Open Core 模式不是 Autional 的发明。已有一批成功公司验证了它的可行性：

- **GitLab**：开源自托管版（CE）与企业版（EE）。开源版功能完整到足以让 GitLab 成为 GitHub 的主要竞争对手，但企业功能（合规、高级安全扫描、Epic 层级）才是商业版的核心价值。
- **Supabase**：核心开源（数据库、认证、存储），商业版提供托管、自动扩缩容、SOC 2 合规。其开源版被数万名开发者自托管，商业版服务需要 SLA 保障的企业。
- **Grafana**：开源监控可视化平台，商业版提供企业插件、LDAP 集成、审计日志。

这些公司的共同点是：**开源版本身就是一款优秀产品，而不是商业版的广告。** 这是 Autional 努力达到的标准。

## 我们对开发者的承诺

如果你是想为自己的项目寻找身份方案的独立开发者或小团队：

1. **Autional 的开源版对你完全免费**，没有功能限制，没有用户数上限
2. **如果有一天你不再需要 Autional**，你的数据可以通过标准 API 导出——我们不会把你锁死
3. **我们不会突然变更开源许可证**——已开源代码的 AGPL-3.0 授权是永久且不可撤销的

如果你已经在使用 Autional 的企业客户：

1. 你的商业授权费用**直接资助开源开发**——你支付的费用让独立开发者与小团队可以免费使用 Autional
2. 如果你对某个商业功能有反馈，可以提交功能需求——我们的路线图优先级在很大程度上由付费客户需求驱动
3. 如果你对某个开源功能有反馈，可以提交 PR——就像在任何开源项目里一样

## 我们仍在摸索

Open Core 模式让项目能够维持持续的研发投入并逐步壮大团队。但我们也清楚，这个模式需要持续的信任维护。

每当我们新增一个商业功能，就会有人质疑「Autional 是不是在走向闭源」。我们理解这种担忧，只能用行动回应——持续把核心组件开源、把产品规划公开，是我们对这个问题唯一的回答。

**透明不是一次性声明，而是每天的选择。** 本文本身就是这种透明的一部分——我们不希望你想象中的 Autional 是一个完美的开源乌托邦，而是希望你了解我们真实的取舍与挣扎。

如果你对我们的开源策略有疑问或建议，欢迎直接在 GitHub 仓库中提交 Issue。我们会在那里回应——公开回应，不走私下工单。
